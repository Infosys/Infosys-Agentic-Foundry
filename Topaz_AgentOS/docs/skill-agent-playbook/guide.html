Building Skill-Based Agents

A practical guide: what a skill is, how to author it, what the platform underneath must provide, and how it all runs together.

For engineers & architects · vendor-neutral · read top to bottom or jump around

1The idea in one minute

Instead of building one large agent that tries to do everything — with its prompt, its logic, its security, and its knowledge all tangled together — you build small, focused units called skills, and you run them on a shared platform called a harness.

The split is simple:

  • A skill is the thing you author — it describes a job, the knowledge to do it, the tools it may use, and the rules it must follow.
  • The harness is the thing that runs it — it routes a request to the right skill, drives the reasoning loop, provides shared capabilities (tools, models, memory…), and enforces security.

The payoff is reuse (write a skill once, use it everywhere), governance (security and audit live in one place), portability (a well-packaged skill can move between platforms), and speed (new behaviour is a new skill, not a rewrite).

The rest of this guide goes concrete-first: the skill you build → its contract → the knowledge it reads → the harness that runs it → what that harness must provide → how a single request flows through all of it.

2What is a Skill?

A skill is a self-contained unit of capability, knowledge, and governance for one class of tasks — not just a system prompt. You ship it as a folder:

my_skill/ manifest.(yaml|json) # the host contract (how to install it) DEFINITION.(md|yaml) # the agent definition (persona + instructions) README.md # what it does, how to use it contexts/ # knowledge it reasons over tools/ # custom capabilities (small programs) hooks/ # governance handlers, scoped to this skill viewers/ # HTML result cards / pages fixtures/ tests/ # demo data + smoke tests

Only three things are mandatory — a manifest, a definition, and at least one source of knowledge or capability. Everything else is opt-in:

manifestdefinitioncontextstoolshooksviewersfixturestests

Most skills grow through three tiers — start minimal and add as the use case demands:

TierContainsUse when
Minimalmanifest + definition + (contexts or tools)an advisor / knowledge-plus-prompt skill
Typical+ contexts + tools + READMEmost real skills
Full+ hooks + viewers + fixtures + testsregulated, human-in-the-loop, or customer-facing

Mindset shift: if you're writing one enormous prompt that does ten jobs, that's the signal to split it into several skills with a routing or orchestrator skill on top.

3The definition & the manifest

A skill carries two descriptions of itself, for two different readers:

  • The definition is read by the agent runtime — it shapes the prompt. It holds the persona/instructions plus frontmatter: the execution mode, the tools it may bind, its approval rules, what it's entitled to touch, and pointers to its context files.
  • The manifest is read by the host installer — it decides whether the platform can run this skill at all. It declares what the skill needs, never how the host provides it.

Example — a manifest

spec_version: "1.0"
name: ap_invoice_triage
agent_type: react              # react | workflow | orchestrator …
recommended_model:             # by TIER, never a vendor/model ID
  primary: { tier: frontier }
  light:   { tier: fast }
requires:                       # the host must provide these
  tools:   [run_sql_query, request_human_approval]
  network: [outbound_http]
  hooks:   [pre_tool, post_tool]
inputs:  [{ name: finance_api_key, type: secret }]
outputs: [{ name: triage_result,  type: json   }]

The portability rule: recommend models by tier (frontier / fast / fallback), never by a hardcoded model ID. The host maps the tier to a concrete model it actually has. The same rule applies to hosts, ports, and credentials — declare, don't hardcode.

4Context files & the knowledge hierarchy

A context file is authored markdown that a skill reasons over — a policy, a playbook, a schema, a glossary. It is curated knowledge, owned by domain experts, versioned like source. One context file can be referenced by many skills (author once, reuse everywhere).

The mistake to avoid is dumping every policy into the prompt — it blows the token budget and buries the signal. Instead, structure knowledge as a hierarchy and inject only the matching slice per request. The typical structure is a root index (a routing map of domains → skills → pointers) on top of an L1–L5 taxonomy:

LevelMeaningHolds
L1 — Domainbroadest business areaname, scope, the skills that serve it, pointers
L2 — Process groupa major area within the domaina heading that groups related processes
L3 — Processmaps to exactly one skillthe smallest routable unit
L4 — Sub-process (optional)grouping of activitiesused only when an L3 is large
L5 — Activityatomic task (verb + noun)the leaf a request is matched against + a 1–2 line description

Example — one branch

L1 Domain Widget Operations L2 Group Widget Lifecycle L3 Process Widget Provisioning → skill: widget_ops L5 Activity Allocate widget pool — reserve widgets for a team L5 Activity Rotate credentials — refresh integration keys

Each leaf carries its full path, so a vague request — "how do I get widgets for my project?" — matches Allocate widget pool, routes to widget_ops, and the harness injects only that branch.

How to author it well

  • Write the root index first; keep it a routing table, not a knowledge dump.
  • Bind each L3 to exactly one skill — that binding is what makes it routable.
  • Write descriptive L5 leaves (verb-noun + a sentence) so informal language still matches.
  • Reuse a context file across skills instead of copying it.

Keep context and memory distinct. Context is authored and versioned; memory is learned from past runs. Letting stale learned facts override authored policy is a classic source of an agent "going off-script."

5What is the agent harness?

The harness is the runtime that actually runs your skills. Given a request, it does six things:

  1. Routes & loads — picks the right skill and loads its package + the matching context slice.
  2. Runs — drives the reason → act loop (the planner).
  3. Provides capabilities — tools, models, credentials, memory, etc., each behind a stable interface so it can be swapped.
  4. Fires hooks — at every lifecycle point, so governance can observe or gate.
  5. Enforces hard gates — sandbox, entitlement, approval — that nothing can bypass.
  6. Records — evidence and audit under a single trace.

A useful way to picture how the harness arranges all this is as four layers. Trust decreases upward, so the lower layers are the ones that must never be skipped:

Planner / reasoning coredecides what to do — flexible, general
▼
Capability boundariesreplaceable modules that do the work
▼
Lifecycle hooksobserve · gate · enrich · route
▼
Hard security gatesalways enforced — cannot be bypassed

Two rules keep this honest: business logic never lives in hooks, and security never lives in the LLM. And crucially, the harness runs a skill the same way whether the request came from a chat, a schedule, or a queue — there is no second, less-governed path.

6What capabilities must the harness have?

This is the contract a harness owes your skills. Treat it as a checklist when evaluating or building a platform.

Capability catalogue

  • Tool execution — one uniform, logged, sandboxed path for every tool.
  • Model provider — resolves a requested tier to a concrete model; swappable centrally.
  • Credential resolver + vault — secrets supplied by name, never shown to the model or logs.
  • Policy / entitlement engine — decides who may do what to which resource.
  • Evidence / audit — records actions under a trace ID; one store for every entry point.
  • Memory & learning — durable recall; every write observable and prunable.
  • Approval / HITL — pause for a human, resume with the decision in context.
  • Skill router / loader — picks the skill and loads its full package, scoped correctly.
  • Scheduler & queue — autonomous runs that use the same capabilities and gates as chat.
  • Observability / diagnostics — read-only views to prove the runtime matches its design.

Lifecycle hooks

Hooks are how governance is added without editing the core. A capable harness exposes (at least) these events, and lets a hook be scoped to a specific skill and/or tool:

EventFiresCan block?
before / after toolaround any tool callbefore: yes · after: no
before / after modelaround an LLM callbefore: yes
before / after steparound a workflow stepbefore: yes
on errora tool/step throwscompensation
approval resumeresuming a human-gated runyes
schedule firea scheduled runyes
# a post-tool audit hook that fires ONLY for one tool, in ONE skill
post_tool:
  - matcher: run_sql_query     # this tool…
    skills: [fa_ap]            # …and only when fa_ap is active

Each gating hook declares a fail policy — closed (a failure denies the action) or open (proceed with a warning). Security-relevant hooks should fail closed.

Hard gates — the non-negotiables

These run in the runtime regardless of what the planner or a hook decides: sandbox for code/shell, path safety on file writes, a credential vault that redacts secrets everywhere, entitlement as the upper bound on what a skill may touch, and mandatory approval where policy requires it. Hooks augment these; they never replace them.

Maturity model. You don't need everything perfect on day one. Each capability matures through three stages: Observe (it runs and is logged) → Gate (hooks/policy can block it) → Swap (it sits behind an interface and can be replaced). A pragmatic order: make everything observable, gate the risky paths (tools, credentials, approvals), then make the high-value capabilities swappable.

7How it all runs — one request, end to end

Here is a single request flowing through everything above. The same pipeline applies whether it arrived from a chat box, a cron schedule, or a work queue:

  1. Route — an identity signal (who/what) + a process signal (scoring the request against L5 leaves) pick the skill.
  2. Load — the harness loads the skill package and injects only the matching context slice.
  3. Plan — the reason→act loop decides which capability to call next.
  4. Hook (pre) — scoped hooks may gate the action before it happens.
  5. Hard gate — sandbox / entitlement / approval are enforced by the runtime.
  6. Execute → Hook (post) → Evidence — the capability runs; post-hooks observe; the action is recorded.
  7. HITL if needed → Respond — pause for a human on consequential actions, resume, then answer.

One thread ties it together: a single trace_id is created at the entry point and inherited through every step — route, plan, tool, hook, approval — so the whole run is one auditable story. A scheduled or queued run enters at step 1 with a service identity and flows through the exact same capabilities, hooks, and gates.

8Apply it

Authoring a skill — the workflow

  1. Decompose — state the job in one sentence; if it needs an "and," split it.
  2. Define — persona, execution mode, and the tools it may use (least privilege).
  3. Add knowledge — put policies/playbooks/schemas in contexts/; reference them.
  4. Wire tools — only what it genuinely needs; declare them in definition + manifest.
  5. Govern — encode approval thresholds; add scoped hooks for audit/gating.
  6. Test & package — a happy-path and a "must refuse" smoke test; add the manifest + README.

Evaluating a harness — what to verify

  • A single trace_id inherits across chat → schedule → tool (never minted mid-run).
  • Secrets never appear in previews, logs, or the prompt.
  • Credential-bearing actions fail closed when required context is missing.
  • Turning hooks off restores identical baseline behaviour (they're additive).
  • Declared capabilities match the live runtime (no drift).
  • Scheduled / queued runs use the same gates and hooks as chat.

In one line: keep the reasoning core small and general; push what an agent knows, can do, is allowed to do, and how it shows results into portable skills; and run them on a harness that makes every capability observable, gateable, and swappable on top of security gates that can never be skipped.
