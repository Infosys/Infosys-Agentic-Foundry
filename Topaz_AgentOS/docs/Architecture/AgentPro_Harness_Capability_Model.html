AgentPro harness capability model

One governed enterprise harness, assembled into flow-specific capability profiles. Domain skills and context remain outside the core.

ENTERPRISE HARNESS FLOW PROFILES DOMAIN PACKS AGENTPRO / AGENTOS
Architecture decision

Do not build a separate forked harness for every enterprise domain. Build one stable control plane and runtime contract, then compose different harness profiles for research, coding, business workflows, IT operations and analytics. Create a new core only when the trust boundary or execution substrate is fundamentally different.

Three-layer product boundary

AgentPro / AgentOS platform Stable core
Identity, tenant isolation, policy, model/provider access, orchestration contracts, tool governance, audit, traces, approvals, durable execution and evaluation.
Flow-specific harness assemblies Capability profiles
A selected bundle of tools, runtimes, control policies, evaluators, state machines and UI patterns optimized for a class of work.
Tenant and industry layer Domain packs
Enterprise-specific skills, context, ontologies, workstreams, policies, connector configuration and solution-module UI.

The core owns invariants. Profiles own execution affordances. Domain packs own business meaning.

Inspect a capability profile

Fit with the current AgentPro architecture

Already reusable
SafeKernel, RBAC and audit; provider contracts; model registry; skill routing; React / workflow / parallel / supervisor modes; memory; traces; approvals; queues, scheduler and RL/evaluation sidecars.
Next abstraction to formalize
A declarative CapabilityProfile or HarnessProfile that selects tool providers, execution runtime, state store, approval policy, evaluator suite, limits and supported artifact contracts without changing SkillAgent.
Test for creating a separate harness

Split the runtime only if the workload needs a materially different sandbox, trust boundary, latency/durability model, or deployment topology. Different domain vocabulary, prompts, data sources or approval rules are not enough—they belong in skills, context, policies, connectors and profile configuration.
